# Prompt: redesign LUMEN's web UI to a premium quality bar

Paste everything below the line into a fresh Claude Code session (Opus, high effort) opened in the LUMEN repository.

---

## Role and goal
You are a senior product designer and front-end engineer with real WebGL experience. Redesign the LUMEN web UI to a **premium, hand-crafted quality bar** (think award-winning product site, not a template) while keeping every existing capability and every honesty guarantee. LUMEN restores low-light photos; it is live on Google Cloud Run, runs on CPU, and a restoration takes about 3-6 seconds, so the interface has to make those seconds feel alive and honest.

The look and feel must be **original**. Do not copy any existing product's layout, copy, colours, typography or signature effect one-to-one. The bar is the *craft*: spacing rhythm, typography, meaningful motion, micro-interactions, zero visual jank.

## Read first, in this order
`IMPROVEMENT_PHASES.md` (decision record), `docs/ARCHITECTURE.md`, `docs/DESIGN.md` section 3, `app/server.py` (API), `app/service.py`, `app/web/index.html`, `app/web/details.html`, `app/web/static/css/lumen.css`, `app/web/static/js/workspace.js` and `details.js`, `app/web/static/data/evaluation.json`, `tests/test_web.py`, `tests/test_stream.py`, `tests/test_overlays.py`, `eval_P1_T66.md` sections 9 and 10.

What exists today (keep all of it working): upload by drop / paste / picker; three styles (Natural, Highlight-safe, Quick); live restoration stages over Server-Sent Events (`/api/restore/stream`: queued, decoded, analysed, restored, refined, done) with real timings and a plain-English report; before/after slider; shared zoom/pan/pinch; "What changed" overlays with measured coverage; compare-all-styles; save side-by-side PNG; PNG download; a technical details page with evaluation tables and a "how far can these numbers be trusted" table; light and dark themes; phone, tablet and desktop layouts.

## Design intent
- Concept: **light returning to a dark photograph.** Dark-first, with a genuine light theme (not an inversion). A restrained palette with one warm light accent; confident type hierarchy; a motion language built on light (soft exposure, falloff, bloom used sparingly).
- Avoid generic "AI product" tropes: purple gradients, gradient text, glows on everything, sparkle emoji, "New ✨" badges, uppercase tracked labels everywhere, glossy blobs, pulsing dots.
- Choose **one signature interaction** that is driven by *real data from the pipeline*, not decoration, and justify it in the brief. Examples to choose from or beat: a "develop" scrubber that takes the photo from dark to restored along the real per-pixel change; a before/after histogram morph from real pixel data; a relief of the photo's real brightness map. It must degrade gracefully.

## Experiences to deliver
1. **Landing (first view).** Full-viewport interactive scene in raw WebGL2 (no libraries): a dark photograph the visitor lights with pointer or touch, revealing the restored photo beneath. Use pre-rendered before/after pairs of the bundled example photos, generated by a new script `scripts/make_landing_assets.py` that runs the real pipeline (assets in `app/web/static/img/landing/`, each <= 150 KB, provenance added to `app/examples/SOURCES.md`). Fallback when WebGL is unavailable, `prefers-reduced-motion` is set, or `Save-Data` is on: a static, equally good composition with the same message. Short concrete copy, no hype; drop zone, example thumbnails, and a one-line privacy statement (photos are processed, not saved).
2. **Workspace.**
   - Style picker redesigned with plain-language descriptions. When the `analysed` event reports input noise sigma >= 0.025, show an evidence-based hint that Highlight-safe handled very noisy photos better in our tests (see `eval_P1_T66.md` section 10.4). Show nothing otherwise.
   - **Pipeline strip:** a beautiful staged visualisation driven only by the real SSE events, with per-stage timing, captions built from reported fields, queue position, cancel, and a small real visual per stage (for example a brightness gauge and category from the `analysed` event). No fake progress bars, no timers pretending to be progress.
   - **Result tools:** keep slider, zoom/pan/pinch, overlays, compare-all, side-by-side, downloads. Add a **spotlight (lens) compare** mode: a circular loupe following the pointer or finger that shows the other version inside it.
   - **Diagnosis and checks:** plain-language chips (lighting category, brightness percent, noise level class, clipped-highlight percent) and a short audit. Every chip maps to a reported field. Additive backend fields are allowed (for example a tiny input histogram) only if restored pixels stay identical and a test proves it.
   - **Diagnostic maps drawer:** the real maps (change masks already exist; add the model's light-up map as a small grayscale PNG), requested on demand so the default payload stays small (budget: at most +300 KB).
   - No model names and no research jargon anywhere in the workspace. Plain words only.
3. **Evidence page** (replaces the evaluation part of the details page): designed data visualisation in **inline SVG, no libraries**: results with 95 % intervals (forest-plot style), ablation, and a chart of results by input-noise band that shows the high-noise limitation plainly. All numbers come from the generated data files (`evaluation.json` and `results/phase_f_hardening/summary.json` via the existing generator); never hand-type a result. Include limitations, ethics, licences and reproduce commands.
4. **How it works:** an SVG pipeline diagram with light animation, what each style does, what is and is not stored, and limits.
5. **Shell:** navigation, footer, theme toggle (system by default, manual override remembered with try/catch around storage), skeleton loaders, empty states, error and offline states, toasts, a real 404 page.

Non-goals: webcam or live mode, Zero-DCE++ or fusion features, accounts, analytics, external fonts/CDNs/libraries, new model features.

## Hard constraints
- **No build step.** Plain HTML, CSS and ES modules under `app/web/`. No vendored libraries. Fonts: system stack, or self-hosted SIL-OFL variable fonts totalling <= 120 KB with their licences added to `THIRD_PARTY_NOTICES.md`, `font-display: swap`.
- **CSP stays exactly as it is:** `script-src 'self'`, `style-src 'self'` (no inline styles or scripts; setting CSSOM properties from JS is fine), `img-src 'self' data: blob:`, `connect-src 'self'`. Shaders as same-origin `.glsl` files or JS template strings. No request leaves the origin.
- **Frontend-first.** Backend changes must be additive, tested, and must not change a single restored pixel (the existing identical-output tests must keep passing untouched).
- Never weaken the tests for: CSP, no external resources, no inline style, identical pixels, upload deletion, plain-language workspace. You may update other tests when the UI changes on purpose; list every change and why.
- **Performance budget:** landing LCP < 2.0 s on a mobile profile with 4x CPU slowdown; CLS < 0.05; total JS <= 120 KB gzipped; the WebGL loop pauses when the tab or canvas is off-screen; target a steady 60 fps on a mid-range laptop and a graceful reduction on phones.
- **Accessibility:** WCAG 2.2 AA; **axe 0 violations** on every page and state in light, dark, phone and tablet; everything operable by keyboard; visible focus; touch targets >= 44 px; screen-reader announcements for stage changes; `prefers-reduced-motion` and `forced-colors` honoured; the WebGL canvas is decorative and has equivalent static content.
- **Honesty:** the UI states only values the pipeline reported. No invented metrics, no fake progress, no claims beyond the evidence in `eval_P1_T66.md`. Show the high-noise limitation where it matters.
- **Naming:** LUMEN is this team's own project. Never name any other team's project or product in code, docs, comments or commit messages; describe things on their merits.
